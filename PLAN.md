# Plan: ZSA Voyager base-layer switching (Mac ⇄ Omarchy)

Hand-off plan for Claude Code. Read this whole file before changing anything.
The scripts in `host/` already work. An earlier version was tested on real hardware on macOS
(`status`, `toggle`); the current version is tested against the firmware model in `host/tests/`.
Build on them; don't rewrite them from scratch.

## 1. Goal

One repo that lets me switch my ZSA Voyager between two base layers:

| Layer | Name      | Used for                       |
|-------|-----------|--------------------------------|
| 0     | `mac`     | primary, work, most of the day |
| 1     | `omarchy` | secondary, Arch + Hyprland     |

Two parts, usable separately or together, neither treated as second-class:

- **A. Host scripts.** `voyager-layer` / `voyager-test` talk to the keyboard over raw HID using ZSA's
  Oryx protocol. They need no Keymapp and no kontroll, and work on stock Oryx firmware too.
- **B. Custom firmware.** The Oryx layout is built with a small amount of extra QMK code through
  ZSA's GitHub Actions template.

`voyager-layer status` must keep working in every mode. It's my main "what is the keyboard doing" check.

## 2. Decisions already made

- **The OS decides and triggers the switch.** Firmware OS detection is optional and **off by default**,
  because I use a USB hub and detection is a heuristic that hubs can fool. Omarchy switches the layer
  itself: via udev when the keyboard is plugged in, and via Hyprland autostart at login.
  The Mac needs nothing: the board powers up on layer 0.
- **Base layers live in QMK's *default layer*, not in `layer_state`.** The custom firmware "folds" any
  request to turn on layer 0 or 1 (from the script, `TO()` keys, …) into `default_layer_set()`. Effects:
  - the script and the firmware always agree on the active base (see §4.2),
  - the status LEDs stay dark on **both** base layers, because the stock Voyager LED code only looks at
    `layer_state`, while layers 2+ still light the LEDs as usual.
- **Switching to a base layer also makes the keyboard go quiet.** In the same hook, when the pairing
  flag is set, the firmware sends one LAYER event (a reliable reply for the script) and then clears
  the flag. After that the keyboard sends nothing over raw HID (no key events, no layer events) until
  something pairs again.
  - Keymapp keeps full functionality: opening it pairs, and everything flows. The flag may stay set
    after Keymapp closes, until the next base switch or power loss. That is fine.
  - There is **no** timer and **no** key-event suppression hook. Both were considered and dropped.
  - Known trade-off: pressing a `TO(0)`/`TO(1)` key also clears the flag, so Keymapp's live view stops
    until Keymapp is reopened. Accepted. Don't add code to tell key presses and host commands apart.
- **Stock firmware keeps working with the scripts**, and just leaves the flag set (that's stock behaviour).
- **The LED watcher (`voyager-layer leds`) is stock-firmware-only and optional.** It isn't installed by
  default. With the custom firmware it's pointless (LEDs are already dark) and would stop receiving
  events after the first base switch.
- **A Hyprland keybind to toggle layers is optional, not required right now.** Ship it as a commented
  snippet that the installer can enable with a flag.

## 4. Background (verified in source, Sept 2026)

Sources: `zsa/qmk_modules` → `oryx/oryx.c`, `oryx/oryx.h`; `zsa/qmk_firmware` branch `firmware25` →
`keyboards/zsa/voyager/voyager.c`, `quantum/action_layer.c`, `quantum/os_detection.*`,
`lib/python/qmk/cli/generate/community_modules.py`. Re-check if the firmware version has moved on.

### 4.1 Protocol

**Transport.** Raw HID, usage page `0xFF60`, usage `0x61`, 32-byte reports, vendor ID `0x3297`.
- On Linux, use `/dev/hidrawN` and write `0x00` (report ID) + 32 bytes.
- On macOS, use hidapi (`pip install hidapi`, **not** `hid`).

**Every command the stock firmware handles:**

| Code | Command | Notes |
|------|---------|-------|
| `0x00` | GET_FW_VERSION | |
| `0x01` | PAIRING_INIT | Sets the flag instantly (no key sequence). Replies `0x04` PAIRING_SUCCESS, then `0x05` LAYER (live value). |
| `0x02` | PAIRING_VALIDATE | no-op, kept for old clients |
| `0x04` | SET_LAYER `[on, layer]` | `on=1` → `layer_move(layer)`. Ignored unless paired. |
| `0x05` / `0x06` / `0x09` | RGB control / set one key light / set all | |
| `0x07` | SET_STATUS_LED `[idx, on]` | takes LED control from the firmware |
| `0x08` | brightness up/down | |
| `0x0A` | STATUS_LED_CONTROL `[0/1]` | `0` hands LED control back to the firmware |
| `0x0B` / `0x0C` | automouse set/get | |
| `0xFE` | GET_PROTOCOL_VERSION | |
| anything else | → error reply | `0x03` DISCONNECT is in the enum but **not handled** |

**Events.** `0x05` LAYER `[layer]` = `get_highest_layer(layer_state | default_layer_state)`.
`0x06` KEYDOWN / `0x07` KEYUP `[col, row]`.

**The pairing flag** (`rawhid_state.paired`) is a boolean in the keyboard's RAM, not a connection.
- It starts off at power-up.
- It gates SET_LAYER. While it's set, the firmware also pushes a report on every key press/release
  and every layer change. If no program has the interface open, the OS discards those reports.
- Stock firmware only clears it on power loss, or when a report can't be handed to the host within
  100 ms (not expected in practice).
- It's separate from `status_led_control`, which is the only thing that affects the LEDs.
- `raw_hid_receive` in `oryx.c` is not weak, so custom code can't replace the command handler.
  `rawhid_state` (extern) and `oryx_layer_event()` are declared in `oryx.h` and can be used from custom code.

**Hook order in `layer_state_set`:** modules (oryx) → `_kb` → `_user`; `layer_state` is assigned after.
So the oryx module's own event is computed before our hook runs, and can be stale or missing when the
fold changes the default layer. That's why the custom hook sends its own event via `oryx_layer_event()`.
By then `default_layer_state` is already updated, and `layer_state` still holds the old value (which is
normally 0, because base layers never sit in it).

**Voyager LEDs** (`VOYAGER_USER_LEDS` undefined, host not in control): `layer_state_set_kb` shows
`get_highest_layer(state)` in binary, using the state returned by the user hook.

### 4.2 Why the fold hook is required

Without it, once the default layer is 1 (OS detection or a `DF()` key), `voyager-layer mac` does
`layer_move(0)`, but key lookup uses the highest of `layer_state | default_layer_state`, which is still 1.
The model reproduces this (`Stock.test_default_layer_conflict_is_reported`). The script reports
`error: asked for mac (0), keyboard reports omarchy (1)`.

### 6.1 `base_layers.h`

```c
#pragma once
#include QMK_KEYBOARD_H
#ifndef BASE_MAC
#    define BASE_MAC 0
#endif
#ifndef BASE_OMARCHY
#    define BASE_OMARCHY 1
#endif
layer_state_t base_layers_fold(layer_state_t state);
```

### 6.2 `base_layers.c`

```c
#include "base_layers.h"

// Any request to turn ON a base layer (host SET_LAYER -> layer_move, TO(), TG(), ...)
// becomes a default-layer change. Base layers never stay in layer_state, so:
//  - host scripts and firmware agree on which base is active,
//  - the stock Voyager LED code shows nothing on either base.
// When a host is paired, it also answers with the new layer and clears the
// pairing flag, so the board stops sending key/layer reports until something
// (Keymapp, voyager-layer) pairs again.
// Uses default_layer_set (RAM only), never the persistent variant.
layer_state_t base_layers_fold(layer_state_t state) {
    const layer_state_t mask = ((layer_state_t)1 << BASE_MAC) | ((layer_state_t)1 << BASE_OMARCHY);
    layer_state_t requested = state & mask;
    if (requested) {
        uint8_t base = get_highest_layer(requested);
        if (get_highest_layer(default_layer_state) != base) {
            default_layer_set((layer_state_t)1 << base);
        }
        state &= ~mask;
#if defined(COMMUNITY_MODULE_ORYX_ENABLE) && !defined(BASE_LAYERS_KEEP_PAIRING)
        if (rawhid_state.paired) {
            oryx_layer_event();          // reply: reports the new default layer
            rawhid_state.paired = false; // go quiet
        }
#endif
    }
    return state;
}

#if defined(OS_DETECTION_ENABLE) && defined(BASE_LAYERS_OS_DETECTION)
bool process_detected_host_os_user(os_variant_t os) {
    default_layer_set((layer_state_t)1 << (os == OS_LINUX ? BASE_OMARCHY : BASE_MAC));
    return true;
}
#endif
```

**Verify the includes.** Confirm `rawhid_state` and `oryx_layer_event()` are visible here. ZSA's
`voyager.c` uses `rawhid_state` under `COMMUNITY_MODULE_ORYX_ENABLE`. If they aren't visible,
include the module's `oryx.h`.

### 6.3 Wiring

- **`rules.mk`:** append `SRC += base_layers.c`, plus a commented `# OS_DETECTION_ENABLE = yes`.
- **`keymap.c`:** call the fold hook.
  - If Oryx did **not** define `layer_state_set_user`, append:
    ```c
    #include "base_layers.h"
    layer_state_t layer_state_set_user(layer_state_t state) { return base_layers_fold(state); }
    ```
  - If it **did**, add `state = base_layers_fold(state);` as the first line of the existing function, and
    flag it in the docs as a spot to re-check after Oryx updates.
- **`config.h`:** append a clearly marked, commented-out options block:
  ```c
  // --- base layer options ---
  // #define BASE_LAYERS_OS_DETECTION      // pick base layer from detected host OS (needs OS_DETECTION_ENABLE)
  // #define OS_DETECTION_KEYBOARD_RESET   // re-detect when a KVM/switch changes hosts without power loss
  // #define BASE_LAYERS_KEEP_PAIRING      // don't clear the pairing flag on base switches
  ```
- **Optional keys:** `TO(0)` / `TO(1)` keys set in Oryx now act as "switch base layer" keys. They also
  clear the pairing flag (see §2). No `DF()` keys are needed.

## 7. Phase 3: host side

### 7.1 `host/voyager-layer` (exists)

Commands: `mac | omarchy | toggle | status | events [secs] | leds | <n>`.
Options: `--wait SECS`, `--notify`, `--setup`.

**Backends:**
- Linux uses hidraw (stdlib only).
- macOS uses hidapi in a private venv (`~/.local/share/voyager-layer/venv`). `--setup` creates it, and
  the script re-launches itself inside it automatically.

**Environment variables:** `VOYAGER_LAYERS="mac=0,omarchy=1"` and `VOYAGER_BACKEND=hidraw|hidapi`.

**Switch flow** (`switch()`):
1. Send SET_LAYER.
2. Read the LAYER event; if it matches, done.
3. Otherwise, re-pair and query. If that shows the target, send SET_LAYER once more, so custom firmware
   goes quiet again after the re-pair. Retry once, then fail with a clear error.

**`status`** prints the layer. If it's a base layer, it re-selects it (`quiet()`), which has no visible
effect and makes custom firmware go quiet. If a non-base layer is active (e.g. `TG(3)`), it changes nothing.

**`events`** is the debug dump used for acceptance. Afterwards it goes quiet the same way.

Tasks:
- Keep `host/tests/test_voyager_layer.py` green, and add cases for anything new.
- `.github/workflows/host-tests.yml` runs on changes to `host/**`:
  `python3 -m unittest` (from `host/tests`), `python3 -m py_compile host/voyager-layer`,
  `shellcheck host/voyager-test host/install.sh`, and `bash -n`.
- Optional, low priority: a config file at `~/.config/voyager-layer/config` as an alternative to the env var.

### 7.2 Omarchy (`host/linux/`)

- **`70-zsa-voyager.rules`:**
  ```
  KERNEL=="hidraw*", ATTRS{idVendor}=="3297", TAG+="uaccess"
  ACTION=="add", SUBSYSTEM=="hidraw", ATTRS{idVendor}=="3297", TAG+="systemd", ENV{SYSTEMD_USER_WANTS}+="voyager-omarchy.service"
  ```
  - `ATTRS` walks parent devices, so this works through a USB hub.
  - The board has several hidraw nodes, so the unit may be triggered more than once. That's harmless (oneshot, idempotent).
  - The user unit only starts once a user session exists. At boot, the Hyprland autostart line covers it.
- **`voyager-omarchy.service`:** oneshot, `ExecStart=%h/.local/bin/voyager-layer omarchy --wait 5`.
- **`hyprland.conf`** snippet for Omarchy's `~/.config/hypr/autostart.conf` and `bindings.conf`:
  ```
  exec-once = $HOME/.local/bin/voyager-layer omarchy --wait 5
  # Optional manual toggle (not required yet):
  # bindd = SUPER CTRL, K, Toggle Voyager base layer, exec, $HOME/.local/bin/voyager-layer toggle --notify
  ```
  Verify the keybind combo is unused in the current Omarchy defaults before suggesting it.

### 7.3 macOS (`host/macos/`)

- Nothing runs automatically. The board powers up on layer 0 (Mac), and nothing pairs unless I run the
  script or Keymapp.
- The installer runs `voyager-layer --setup`.
- Optional LaunchAgent for `leds`, stock firmware only.
- **Future / optional, don't build it yet:** if my hub turns out to switch computers without cutting
  power, the Mac would need a plug-in trigger, e.g. a Hammerspoon USB watcher running
  `voyager-layer mac`. Just document it.

### 7.4 `host/install.sh`

`install.sh [--keybind] [--leds] [--uninstall]` detects the OS.
- **Always:** copy both scripts to `~/.local/bin`.
- **Linux:**
  - install the udev rule (sudo, prompt first) and run `udevadm control --reload`,
  - install the user unit and run `daemon-reload`,
  - **print** the Hyprland snippet rather than editing configs silently. With `--keybind`, append it,
    guarded by a marker comment so re-runs don't duplicate it.
- **macOS:** run `--setup`. With `--leds`, install and load the LaunchAgent (expand `$HOME`).
- `--leds` prints a warning that it's only useful on stock firmware.
- Must be idempotent and pass shellcheck.

## 9. Manual test checklist (for me, after flashing)

1. **Mac:** `voyager-layer status` → `mac (0)`. Then run `voyager-test` and answer the prompts in a text
   editor. All should pass, with the LEDs dark on both bases.
2. **Mac:** hold a key for a layer ≥2 → LEDs light up. Release → dark.
3. **Mac:** `voyager-layer events 10`, then type → key events show. Then `voyager-layer mac`.
4. **Omarchy:** plug in through the hub → `voyager-layer status` → `omarchy (1)` within ~1 s, with no manual steps.
5. **Omarchy:** reboot, log in → `status` → `omarchy (1)`, via autostart.
6. **Omarchy:** `voyager-test toggle` → Enter flips the layer, and the editor shows the change each time.
7. **Omarchy (optional):** the keybind toggles the layer and shows a notification.
8. **Either OS:** open Keymapp → live view works; a `TO()` key freezes it (expected); reopen → works again.
